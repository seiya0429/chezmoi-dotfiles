# Git: 変更調査・分割コミット

## 目的

作業ツリーの変更を把握し、**論理単位**ごとに分け、各コミットに**日本語の適切なメッセージ**を付けて**分割コミット**する。

## 前提の確認

- ブランチ名・ベースブランチ・リモートの有無はユーザー指示がなければ `git status -sb` と `git branch -vv` で確認する。
- ユーザーが Conventional Commits 以外を指定していればそれに従う。未指定なら Conventional Commits を既定とする。
- **コミットメッセージの言語は既定で日本語**（件名・本文）。ユーザーが英語や別言語を明示したときだけそれに従う。

## ワークフロー（チェックリスト）

```
- [ ] 1. 変更の全体像を把握する
- [ ] 2. コミット単位にグルーピングする
- [ ] 3. 各グループのコミットメッセージ案を書く（既定は日本語）
- [ ] 4. ユーザーにグループとメッセージを提示し、問題なければ実行する
- [ ] 5. 各コミット後に状態を確認する
```

## 1. 変更の調査

次を実行して、**ファイル単位**と**内容**の両方を把握する。

| 目的 | コマンド例 |
|------|------------|
| ブランチ・追跡・作業ツリー | `git status -sb` |
| 未ステージの差分 | `git diff` |
| ステージ済みの差分 | `git diff --cached` |
| 特定ファイル | `git diff -- path` |
| リネーム検出 | `git diff --find-renames` |
| 直近の文脈 | `git log -5 --oneline` |

**読み取ること**: 新規/削除/リネーム、設定とコードの混在、フォーマットのみとロジック変更の混在、依存関係ファイル（lock）の更新が他と一緒になっていないか。

## 2. 分割の粒度（グルーピング）

次は**別コミット**に分けるのが一般的。

- **異なる関心事**: 例）バグ修正とリファクタ、機能追加とドキュメント
- **レビューしやすさ**: 1コミットが1ストーリーとして説明できるか
- **巻き戻し単位**: あとで `git revert` したときに意味のある単位か
- **生成物と手編集**: 例）フォーマッタ一括適用を単独コミットにする

次は**同じコミットにまとめてよい**ことが多い。

- 同一バグの修正に必要な複数ファイル
- テストと実装が不可分な場合（プロジェクトの慣習に従う）

## 3. コミットメッセージ（Conventional Commits 既定・**件名・本文は日本語**）

形式:

```
<type>(<scope>): <短い要約（日本語）>

[本文: なぜ / 何が変わったか。必要なときだけ。日本語]
```

**type の例**: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`, `ci`

- **件名・本文は日本語**を既定とする（「〜する」「〜を追加」など簡潔な体言止め・ですますのどちらかプロジェクトに合わせて統一）。
- 件名は **50文字前後**を目安に。英語で書くようユーザーが指定した場合は、命令形・現在形の英語慣例に従う。
- 本文や箇条書きは **72文字折り返し**を目安に。
- チームやリポジトリが英語メッセージ必須のときは、ユーザーまたは `CONTRIBUTING.md` の指示に従い英語に切り替える。

## 4. 分割の実行（ステージング）

意図したファイルだけをステージする。

| 状況 | 操作 |
|------|------|
| ファイル全体が1コミット用 | `git add -- path` |
| 1ファイルに複数の論理塊がある | `git add -p`（または `git add -i`） |
| 間違えてステージした | `git restore --staged -- path` |

**推奨手順**:

1. 最初のグループだけをステージ
2. `git diff --cached` でステージ内容を確認
3. `git commit -m "..."`（複数行は `-m` を複数回、またはエディタ）
4. 残りのグループで 1〜3 を繰り返す

## 5. ユーザーへの提示

コミットを実行する前に、少なくとも次を明示する。

- コミットの**個数**と**順序**（依存関係がある場合は理由）
- 各コミットの**含めるパス（または塊の説明）**
- **件名案**（日本語。必要なら本文案）

ユーザーが「そのまま実行」「順序だけ変えて」などと言うまで、破壊的でない範囲で確認する。初回から `--no-verify` 等のフック回避は**ユーザーが明示したときのみ**。

## 6. 完了確認

- `git status` がクリーンか、意図した未コミットが残っているか
- `git log -n <コミット数> --oneline` でメッセージと順序を確認

## 避けること

- 意味のない `wip` や `fix` だけの件名
- 無関係な変更を「とりあえず」1コミットに詰め込む
- lock ファイルや生成物の更新を、無関係なロジック変更と同一コミットに混ぜる（分けられない理由があるときは本文に記す）

## 例: グループ案の出し方

**状況**: `foo.ts` にバグ修正と整形、`README.md` に追記、`package-lock.json` 更新

**分割例**（件名は日本語）:

1. `fix(api): レスポンスのキャッシュキーを修正` — `foo.ts` のバグ修正のみ（整形が混ざるなら先に整形コミットを分離）
2. `docs: インストール手順を README に追記` — `README.md`
3. `chore(deps): 依存関係を lock に反映` — `package-lock.json`（プロジェクトが lock を別コミットにする方針の場合）
